# Точки роста и ограничения

## В первую очередь

1. **Защита от злоупотреблений.** Telegram подтверждает аккаунт, но не личность или телефон. Нужны проверка телефона через согласованный сервис, мониторинг отмен и no-show, политика блокировок и подтверждение администратором подозрительных заявок. Нынешние лимиты по истории — мягкие: параллельные запросы или множество аккаунтов могут их обойти. Для жёстких лимитов нужен централизованный атомарный rate limiter (включая IP/устройство на доверенном прокси), с учётом приватности и общих сетей.
2. **Календарь и данные.** В `api/_lib/schema.ts` старый `SEED` пересчитывает `starts_at` по исходному `day_offset` при каждом запуске `/api/admin/setup`: это может сдвинуть даты. Не запускать на рабочей базе без резервной копии и согласованного исправления. Для новых миграций есть отдельный `/api/admin/migrate-bot-state` без демо-данных; остальные миграции всё ещё нужно отделить от `SEED`, сохранить абсолютные даты и устранить устаревшие смещения в других экранах бота. Убедиться, что в базе нет пересекающихся окон, созданных ранее: запрет пересечений при создании новых окон не исправляет исторические данные и не является ограничением БД.
3. **Гостевые данные.** Ранее браузерные пользователи определялись коротким хешем device ID в том же поле, что Telegram ID. Возможны коллизии гостевых идентификаторов между собой или с Telegram ID и смешение исторических данных. Новые брони, заказы и персональные маршруты доступны только с Telegram; старые данные автоматически не объединяются и не удаляются. Нужен согласованный аудит и миграция гостевых клиентов в отдельное пространство идентификаторов.
4. **Настройка бота.** До публикации задать защищённый `TELEGRAM_WEBHOOK_SECRET` и `SETUP_TOKEN` в Vercel, переустановить webhook через `/api/bot/setup` и проверить `/start`. Без правильного секрета webhook закрыт; без токена или подписи администратора setup недоступен. Провести проверку live Telegram/Neon, включая конкурентные запросы.

## Следующие улучшения

- История заказов теперь загружается из API при входе; нужны отдельные тесты отображения статусов и отмены заказов.
- Полноценная транзакционная модель и ограничения пересечений на уровне PostgreSQL для любых окон/занятий и действий бота; объединение многочасовой аренды в общую группу с отменой целиком (сейчас каждое окно — отдельная запись).
- Подтверждение контактов, реальные уведомления, напоминания и предоплата — только после выбора провайдера и правил клуба.
- Добавить реальные автоматические интеграционные и конкурентные тесты на Neon/Vercel, визуальные тесты в мобильном Telegram и проверку разных часовых поясов. Текущие тесты используют PGlite и эмуляцию, не живой продакшен.
- Переделать сценарий «Свой урок»: текущий API принимает только существующие занятия из каталога, поэтому произвольная заявка не создаётся. Решить, должна ли она быть заявкой администратору или бронированием реально доступного слота.
- Сверить пользовательские тексты, факты о клубе, реальные часы и цены; убрать обещания, которые не обеспечиваются системой. Записи и заказы не должны выглядеть успешными при недоступном сервере.
- Хранить состояние многошаговых действий бота во внешнем хранилище: текущие `Map` теряются между серверными инстансами и перезапусками.
